## 1. 先送りされたもの

`ATH-HIER-018` は v1 の動的な Agent 定義の生成を**既存 persona の組み合わせ**、capability、
既存 `allowed_tools` の部分集合に限定する。Persona の**本文の生成**(roster が covering
しない専門領域のための新しい persona 本文の作成)は、評価のために Phase 8 へ明示的に
先送りされていた(`ATH-HIER-018`)。

## 2. 評価

**利益。** 要求 capability の集合を covering する persona が存在しない場合、階層は
再分解か escalate を迫られる(`ATH-AGENT-005`)。生成 persona は構成可能な階層を広げ、
ロングテールの専門領域での escalate を減らす。

**実装済みアーキテクチャに対して評価したリスク:**

| リスク | 根拠 |
|---|---|
| 生成本文が優先順位のスタックに矛盾する、あるいは独自の権限主張を運ぶ可能性 | `ATH-SKILL-026`/`ATH-SKILL-027` は構成時に skill 文を走査する。同じ走査が skill の**材料**にも適用され、生成 persona 本文は同一の書き込み権限のゲートを要する(`Layer::writable_by` — persona は人間/システムが書く層)。persona 本文を書く生成経路は、`AiprjRules` に隣接する制御表面への新しい書き込み権限である — 制御表面の隔離(`ATH-CORE-043`)が存在するのはまさにこれを防ぐため |
| 生成本文が偽装された権限を与える | 権限整合の監査(P4-04)は wire スキーマと宣言された事実を検査し、自由文は検査しない。公開を担う persona は、定義が保持しない権限を主張するよう Agent に指示でき得る。Runtime の事実は実行を依然として守るが、*persona* の層 — Agent が常時職務として読む — は未監査の文を運ぶことになる |
| 監査可能性 | Persona は version 管理されたファイルで、その来歴はリポジトリ履歴である(`R-PER-05`)。実行時に組み立てられる生成本文には、専用の生成記録(要求者、ソース、チェックサム、承認)が先に着地しない限り、そのような痕跡がない |
| 信頼の基盤 | v1 が persona の内容を信頼するのは、人間が著し review 済みだからである。生成内容は persona を Skill ソースと同じ信頼クラスへ移す — そこでの信頼は検証に基づく(`ATH-SKILL-035`/`036`)。署名と registry 経由の配布は意図的に v1 の要件ではない |

## 3. 再検討の前提条件

Persona 生成を有効化するには、実装の前に次を要する:

1. 受入れ**前に**生成本文へ優先順位の構成チェック(P5-11 の面)を実行し、無効化の試みを
   拒否する生成ゲート。
2. Persona 生成の記録(要求者、組み合わせたソース persona、生成ファイルを materialize する
   場合のチェックサム)と、それを監査するための Event。
3. `pattern` レベルのポリシー設定: どのレベルが生成を要求できるか、`high` の承認
   (`ATH-SKILL-024` の類似)、`ATH-REGISTER` 形式の履歴としての永久保持。
4. 4 点すべてを covering する仕様の改訂 — 実装が先になることは決してない(`ATH-DEV-007`)。

## 4. 決定

`ATH-HIER-018` の組み合わせによる制限が構成の規則であり続け、動的定義の表面
(`ATH-HIER-008`)は既存 persona によって境界される。Persona 生成は、§3 の前提条件が
実装され仕様が改訂されるまで、Phase 8 を超えても対象外である。要件 ID の再利用と撤収は
行わなかった(`ATH-GEN-006`)。
