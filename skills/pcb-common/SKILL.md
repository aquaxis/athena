# PCB開発共通ルール・成果物・レビュー基準（共通パッケージ）

## 0. スキル概要

- **対象工程**: PCB開発の全工程（グランドデザイン設計／システム設計／回路図設計／PCBアートワーク設計／SI解析／PI解析）に共通する基盤定義。
- **適用タイミング**: 全スキルの実行時（各スキルの冒頭で本書を参照し、用語・成果物形式・レビュー基準・エラー対応手順を適用する）。単独実行時も同様に参照する。
- **実行モード**: 本スキルは単独で「作業」を実行するものではなく、全スキルから参照される定義集である。ただし、共通ルールの確認・更新についてのみ単独参照が可能。
- **上書き規則**: 個々のスキル（`pcb-*/SKILL.md`）の個別規定と本書が矛盾する場合、**スキル側の個別規定が優先**される。本書は個別規定が無い事項・全工程共通の事項に適用する。

## 1. エージェントの役割と責任範囲

- 本書を参照するエージェント（各工程スキル）は、本書の定義を契約事項として遵守する。
- 本書の「判断記録フォーマット」「レビューチェックリスト」「エラー対応手順」「引き渡しチェックリスト」は、各工程成果物の品質と追跡可能性を担保するための最低基準である。各スキルはこれを満たす範囲で上書き（強化）できるが、弱めることは原則禁止とする。
- 本書自体の内容を変更する場合、変更の根拠（理由・影響範囲）を判断記録として残すこと。

## 2. 入力資料と前工程からの引き継ぎ情報

- 本書は入力資料を必要としない（参照される側である）。
- 各工程スキルからは、参照時に「参照目的（用語／成果物形式／レビュー基準／ツール連携／エラー対応／引き渡し）」を明示すること。

## 3. 詳細な作業手順

### 3.1 参照手順（全スキル共通）

1. 各工程スキルは、対応する節を必要に応じて参照する（例: 成果物を作成する際は第7節、レビュー実施時は第8節）。
2. 参照先の定義と個別実装が矛盾した場合は、上書き規則（第0節）に従い判断記録に差異と理由を残す。
3. 共通チェックリストの適用結果（合格／不合格と項番）を、レビューレポートに記録する。

### 3.2 設計データの生成・変更における共通手順

1. 変更対象の設計データと版数を確認する。
2. 変更内容を自然言語の変更指示として明確化し、対象ファイルと変更点を一覧化する。
3. 変更を実施する（可能な範囲でスクリプト・CLIで自動化）。
4. 変更後に必ず再検証する（DRC・ERC・解析条件の再実行等）。
5. 変更履歴と版数を更新する（成果物ルールの版管理に従う）。

## 4. 用語集

| 用語 | 定義 |
|------|------|
| 成果物（Deliverable） | 前工程から後工程へ引き渡す文書・データ・ファイル一式 |
| 引き渡し（Handover） | 前工程の成果物が後工程の必須入力を満たし、引き渡し条件が成立して後工程へ委ねること |
| 判断記録（Decision Record） | 設計判断の内容・選択案・根拠・代替案・承認状態を記録した項目 |
| 承認ゲート（Approval Gate） | 次工程へ進む前に人間の承認が必要な確認点 |
| レビューゲート（Review Gate） | 定められたチェックリストに基づき成果物を検証する確認点 |
| 不具合（Defect） | 要求・設計判断基準・製造・検証基準のいずれかに照らして「合致しない」と判明した設計上の問題 |
| 重大度（Severity） | 不具合の影響度分類: S（致命的：要求悪化・出荷不可）／A（重大：性能や信頼性に確実に影響）／B（軽微：条件次第で問題）／C（改善提案） |
| 再検証（Re-verification） | 修正後に、同一の検証条件で再度検証すること |
| 甲案／乙案 | 比較評価対象として提示する複数の設計案の通称 |
| ターゲット仕様 | グランドデザインで確定した、後工程が満たすべき定量的目標値一式 |
| 制約（Constraint） | 技術・商業・規制面で必ず守るべき条件（変更には再判断と承認が必要） |

## 5. 使用するEDA・解析ツール（共通の連携標準）

各スキルは、以下の抽象化に従い、実際に使用するツール名と連携方式を各スキルの第5節に明記する。ツールが存在しない場合、エージェントはファイル交換（テキスト標準格式）で同等の作業を遂行する。

### 5.1 ツール抽象化テーブル

| カテゴリ | 代表的なツール例 | 連携方式 | 自動化レベル |
|----------|------------------|----------|--------------|
| 回路図捕捉 | KiCad、市販回路図キャプチャCAD | CLI（KiCad CLI）、スクリプト（Python等）、ファイル生成 | A（バッチ検証）/ B（回路展開確認） |
| PCBレイアウト | KiCad、市販PCBレイアウトCAD | CLI + スクリプト + ファイル交換 | A（生成・DRC）/ B（配置・主要配線判断） |
| SI解析 | ngspice（OSS）、市販SI解析ツール | コマンドライン実行＋結果ファイル解析 | A（反復解析）/ B（評価・判定） |
| PI解析 | ngspice（OSS）、市販PI解析ツール・専門解析ツール | コマンドライン実行＋結果ファイル解析 | A（反復解析）/ B（評価・判定） |
| 3D / 機械整合 | 電子CAD付属3Dビューア、STEP展開ツール | ファイル交換 | A |
| テキスト標準格式 | Markdown、YAML、CSV、Gerber RS-274X、Excellon drill、.net netlist、IBIS、S-parameters (.s2p等) | ファイル交換 | A |

**ツール表記のベンダー中立ポリシー**: 本スキル群の文書に市販（非OSS）ツールの製品名は記載しない。製品名を記載してよいのは OSS ツール（例: KiCad、ngspice）と標準フォーマット名（Gerber RS-274X、Excellon、IBIS 等）のみである。市販ツールはカテゴリ表記（例: 市販PCBレイアウトCAD、市販SI解析ツール）とし、実際に採用する場合はグランドデザイン工程のツール・形式確定（制約記録・判断記録つき）において**別途明記**して制約として参照する（本書の表へ製品名を追記しない）。

### 5.2 連携上の共通注意事項

1. スクリプト実行は、実行前にファイル・フォルダのバックアップまたは版管理を推奨する。
2. ツール固有の連携が不可の場合は、CSV/YAMLなど汎用形式で中間出力を経由する（FR-1.5: 設計データの生成・変更の代替手段）。
3. ライセンス・実行環境が使用できない場合、該当工程はB（人が実行・C分類）に切り替え、代替手段を成果物に明記する。

## 6. 自動化する処理と人間が承認する処理（共通分類）

| 分類 | 定義 | 具体例（全工程共通） |
|------|------|----------------------|
| **A: 自動化** | エージェントが単独で実行・検証する | 定量的計算、ファイル生成、チェック実行、レポート統合 |
| **B: エージェント実行＋人の承認** | エージェントが起草・実行し、その後人間が承認する | 主要設計判断、後工程へ進む可否、設計データの公開 |
| **C: 人が実行** | 人のみが実行可能 | 商業判断、ライセンス調達、実測データ取得 |

**共通必須承認ゲート**: ①要求の解釈・範囲確認（グランドデザイン冒頭）②主要設計判断（各工程の最重要判断）③後工程への引き渡し直前 ④最終レポート受領時。

**共通ゲートと個別ゲートの対応**（3層は 1 つの系: 共通ルールが「いつ承認を要するか」を定め、各スキルの番号付きゲートはその工程での具体実装。同一内容の承認を二重に要しない・内容が異なるなら別承認）:

| 共通ゲート | 具体実装（各SKILLの番号付きゲート） | 承認対象 | 承認者 | 記録先 |
|------------|--------------------------------|----------|--------|--------|
| ① 要求の解釈・範囲確認 | `pcb-grand-design` 承認ゲート① | 構造化した要求・曖昧語の解釈・制約 | ユーザー/依頼元 | 該当工程成果物の承認記録 + `workflow_state.md` |
| ② 主要設計判断 | `pcb-system-design`①②（ブロック・電源）、`pcb-grand-design`②（採用案）、`pcb-schematic-design`①（部品選定）、`pcb-artwork-design`①②（スタックアップ・配置）、`pcb-si-analysis`①/`pcb-pi-analysis`①（解析プラン）、`pcb-parts-research`①（調査計画・評価基準・データ源同意 — 横断支援工程の承認） | 各工程ごとの最も重大な設計判断 | ユーザー/依頼元 | 各工程成果物の承認記録 |
| ③ 引き渡し直前 | `pcb-grand-design`③・`pcb-system-design`③・`pcb-schematic-design`②（アートワーク開始前リリースレビュー）・`pcb-artwork-design`③（リリース）— いずれも引き渡し承認を兼ねる（各引き渡し別の帰属は直後の全工程適用表） | 後工程に移る成果物一式 | ユーザー/依頼元 | 送信側工程成果物 + 状態ファイル |
| （参考）③の引き渡し実装ではない | `pcb-si-analysis`②・`pcb-pi-analysis`②（解析報告書の受入） | 解析報告書・修正指示書の内容承認。SI/PI→アートワークの差戻し実行（A分類）を担保する承認であり、通常の後工程引き渡しとは区別する | ユーザー/依頼元 | 解析報告書 + 状態ファイル |
| ④ 最終レポート受領 | `pcb-orchestrator` 完了承認 | プロジェクト完了報告書 | ユーザー/依頼元 | 完了報告書の承認記録 |

機械検証（SKILL 第10節の条件・チェックリスト）は A 分類として人承認なしで判定する。人の承認を要するのは B 分類に限定される。各スキルは上記の必須4種を削ることなく、独自の追加ゲートを持てる。

**共通ゲート③「引き渡し直前」の全工程適用**（全ての工程間の引き渡しに適用し、(a) 既存Bゲートの承認が兼ねる、または (b) A分類の機械条件＋既に承認済みの内容に帰着する。いずれでもない引き渡しは進行しない。新たな独立承認を要求しない）:

| 引き渡し | 自体の人的承認 | 帰属 |
|----------|----------------|------|
| グランドデザイン → システム設計 | **B** | `pcb-grand-design` 承認ゲート③が引き渡しを直接承認（③を兼ねる） |
| システム設計 → 回路設計 | **B** | `pcb-system-design` 承認ゲート③（同上） |
| 部品調査（横断支援） → 回路設計 | A | `pcb-parts-research` §10機械条件。調査計画・評価基準・データ源同意（承認ゲート①）が内容を担保。採用判断は回路設計の承認ゲート①で行う（通常の後工程引き渡しではない横断支援の引き渡し） |
| 回路設計 → アートワーク | **B** | `pcb-schematic-design` 承認ゲート②（リリースレビュー）が兼ねる。引き渡し自体は既承認内容の A 分類実行（別個のゲート③は設けない） |
| アートワーク → SI/PI解析 | A | §10.1機械条件。スタックアップ①・配置②の承認が内容を担保（解析は暫定レイアウトへの反復検査） |
| SI/PI解析 → アートワーク（差戻し） | A | 解析報告書受入（SI/PI承認ゲート②）が指摘・修正指示を承認済み。差戻しはその実行 |
| アートワーク → リリース | **B** | `pcb-artwork-design` 承認ゲート③（リリース）が兼ねる |
| 完了報告 | **B** | 共通ゲート④: `pcb-orchestrator` 完了承認 |

## 7. 成果物とファイル形式（共通標準）

### 7.1 成果物文書の構成（Markdown全般）

- 各工程の成果物は Markdown 文書（`.md`）を原則とする。数式は LaTeX 形式でインライン記述する（`$...$`）。
- 表・チェックリスト・判断記録を必ず含む。
- バイナリデータ（回路ソース、Gerber等）は、パッケージMarkdown文書から参照する形とし、パッケージ文書に一覧表を付ける。

### 7.2 版数表記

- 版数は `v1.0`、`v1.1`、`v2.0` の形式とする。版数の変更時には変更履歴節を更新する。

### 7.3 判断記録フォーマット（FR-1.3の共通形式）

各工程成果物の末尾に下記形式で集約する。

```markdown
### 判断記録 D-<工程番号>-<連番3桁>

- **日時**: 2026-MM-DD HH:MM
- **判断内容**: （何を判断したか）
- **選択した案**: （最終的に採用した内容）
- **根拠**: （判断の根拠となる情報・式・測定値・要求仕様の該当章）
- **代替案と不採用理由**: （検討した代替案とその評価）
- **承認**: A（自動）／ B（承認者名・日時）／ C（人・日時）
- **影響範囲**: （この判断が作用する成果物・工程・ファイル）
```

### 7.4 パッケージMarkdownの共通構成

1. 目次（成果物一覧）
2. 各成果物の説明（来歴・妥当性）
3. 判断記録
4. レビュー結果・チェックリスト実施記録
5. 承認履歴

## 8. 検証方法と品質基準（共通レビュー基準）

### 8.1 4大品質基準

1. **完全性**: 成果物が当該工程の必須項目を漏れなく含むこと。
2. **整合性**: 上下流の成果物と矛盾が無いこと（名称・数値・ファイル参照）。
3. **追跡可能性**: 全ての設計判断に判断記録が存在し、根拠が示されていること。
4. **検証可能性**: 検証基準が定量的・定義済みで、同等条件で再実行できること。

### 8.2 共通チェックリスト（全工程適用）

- [ ] 前工程成果物の必須入力を受領し、全て利用した。
- [ ] 定量的計算は全て式・仮定・入力値とともに明記した。
- [ ] 重大な判断には全て判断記録を作成した。
- [ ] 自動検証（DRC・ERC・解析・スクリプト等）を実行した。
- [ ] 不具合があれば修正し、再検証を実行した。
- [ ] 成果物の版数と変更履歴を正しく表記した。
- [ ] 承認ゲートでの承認記録が完備している。

### 8.3 工程別チェックリスト（各スキル第8節で参照される）)

各工程スキルは、上記チェックリストに工程固有の項目を追加して適用する。共通基準との整合を崩さないこと。

## 9. エラー発生時の対応（共通手順: FR-1.7 修正・再検証ループ）

1. **検出**: エラー・不具合の事実を記録する（何が・どこで・いつ）。
2. **記録**: 不具合記録を成果物の「不具合記録」または判断記録の補足に追記する。重大度をS/A/B/Cで分類する。
3. **原因分類**: ①要求・仕様の誤解 ②設計判断ミス ③データ・モデル不備 ④ツール運用ミス ⑤外部要因（部品入手不可等）。
4. **修正指示作成**: 対象・方法・影響範囲・再検証条件を含む指示書を生成する。
5. **修正**: 指示に従い設計データまたは文書を修正する。
6. **再検証**: 修正対象に対応する検証を同一条件で再実行し、結果を記録する。
7. **エスカレーション**: 8節の4大品質基準を満たせない、またはS/A級不具合の解決に商用・権限判断が必要な場合、人間に確認する。

## 10. 引き渡しチェックリスト（共通テンプレート）

各工程スキルの第10節は、本テンプレートに工程個別条件を追加して適用する。

- [ ] 成果物一覧が完備している。
- [ ] 成果物ファイル名・形式が規定に従っている。
- [ ] 判断記録が完備している（全ての重要判断に対応）。
- [ ] レビュー（第8節チェックリスト）が合格し、判明した不具合が全て解決済みである。
- [ ] 承認ゲートの承認記録が揃っている（人によるものは署名相当の記載を含む）。
- [ ] 後工程に必要な情報で、成果物に含まれるべきものが欠落していない。
- [ ] 後工程への依頼内容（特に人来型の作業と期待成果）が明確である。
