# PCB部品調査・選定支援スキル

## 0. スキル概要

- **対象工程**: 基板開発の横断支援（パイプライン外の支援工程）。
- **適用タイミング**: グランドデザイン／システム設計の制約確定後、回路図設計の部品選定（承認ゲート①）前。または設計工程からのデータ要求時。
- **実行モード**:
  - **オーケストレーション連携**: `pcb-orchestrator` がパイプライン外で起動する（通常）。
  - **単独実行**: ユーザーが調査要求（対象機能・制約・評価基準）を提供して起動。
- **目的**: 回路図設計が信頼して採用判断できるよう、出典と取得日時つきの部品候補データを提供する。本スキルは採用判断（部品決定）を行わない — 採用は `pcb-schematic-design` 承認ゲート①の領域である。

## 1. エージェントの役割と責任範囲

- **役割**: 部品候補の収集、データシートからのスペック抽出（出典つき）、入手性・ライフサイクル調査、候補データの引き渡し。
- **責任範囲**:
  1. 要求・制約（電気仕様・パッケージ・温度等級・調達条件）から調査範囲と評価基準を提案し、承認ゲート①で確定する。
  2. 承認されたデータ源のみを照会し、全てのスペック記載に出典（データ源名・URL・照会日時・版/rev）を付ける。
  3. 入手性（在庫・リードタイム・複数供給源）とライフサイクル（量産中・NRFDP／NRND・EOL・代替品の有無）を調査し、根拠を記録する。
  4. 候補データが受け手（`pcb-schematic-design`）の受入条件（第10節）を満たすことを自己検証してから引き渡す。
- **責任範囲外**: 部品の採用決定、回路構成・トポロジー判断、ネット属性・制約値の決定（これらは回路図設計工程の領域）。設計判断そのものは行わない。

## 2. 入力資料と前工程からの引き継ぎ情報

本スキルはパイプライン工程ではないため、固定の「前工程」を持たない。起動時点で利用可能な最新の制約情報を入力とする。

| 入力 | 形式 | 必須 | 出典 |
|------|------|------|------|
| 調査対象一覧（機能ブロック・主要IC/受動部品の種別と要求） | Markdown | 必須 | 依頼者（統括またはユーザー） |
| グランドデザイン仕様書の制約一覧（環境・規制・外部データ源方針を含む） | Markdown | 必須 | `pcb-grand-design` 成果物（確定済みの場合） |
| システム設計仕様書（電源レール・電流・インタフェース仕様） | Markdown | 条件付き | `pcb-system-design` 成果物（確定済みの場合） |
| ユーザーのデータ源同意（照会可能なAPI・DB・サブスクリプション） | テキスト | 必須（外部照会時） | 承認ゲート①で記録 |

**受領確認手順**: ①調査対象ごとに「必須スペック項目」が列挙されていること ②環境等級・規制制約が判明していること ③外部データ源の同意範囲が記録されていること。不備時は第9節に従いデータ要求を発行して停止する。

## 3. 詳細な作業手順

分類: [A=自動化 / B=エージェント実行＋人の承認 / C=人が実行]

1. **[A] 依頼の受領確認**: 調査対象・必須スペック項目・制約の受領を確認する（第2節）。欠落項目はデータ要求として依頼者へ返す。
2. **[A] 調査計画の起草**: 対象ごとに検索キー（MPNパターン・機能キーワード・パッケージ・メーカー）と評価基準（必須/推奨/参考の三段階）を起草し、外れ値基準を定める。**外れ値基準**: 調査対象ごとに、データ源間で乖離する項目や要求値から有意に外れた候補値（例: 必須段階の要求値から一定割合以上の乖離、または同種候補の分布から著しく外れた値）を採用値とせず「要確認」として記録する判断基準。具体例・閾値はゲート①の承認事項（調査計画）に含め、指定がない場合は乖離率50%超またはデータ源間で判定可否が逆転する値を外れ値として扱う。
3. **[B] 調査計画・評価基準・データ源の承認**: 調査計画、評価基準（三段階＋重み）、照会するデータ源一覧（ディストリビュータAPI・部品DB・メーカー網）とその同意範囲を提示し、承認を得る。**必須承認ゲート①（調査計画・評価基準・データ源同意）**。承認前の外部照会は行わない。
4. **[A] 候補収集**: 承認済みデータ源から候補を収集し、各候補に出典（データ源名・URL・照会日時・版/rev）と取得ローデータの所在を記録する。
5. **[A] スペック抽出と照合**: データシートから必須スペック項目を抽出し、要求値との照合結果（充足/不足/要確認）と出典（データ源名・URL・照会日時・版/rev と照合したページ番号）を記録する。読み取れない項目は「要確認」とし、推測で埋めない。
6. **[A] 入手性・ライフサイクル調査**: 在庫・リードタイム・複数供給源（2次供給）・ライフサイクル状態（量産中/NRFDP/NRND/EOL）・公式代替品・後継品を調査し、根拠（データ源・日時）付きで記録する。
7. **[A] 候補表の作成**: 第3.2節の計算式（余裕率・熱初算・ESR等）を適用し、三段階評価基準での適合度（%と適合/条件付き適合/不適合）を付与した候補表を作成する。
8. **[A] 自己検証と引き渡し**: 第8節のチェックリストと第10節の受入条件を確認し、`pcb-schematic-design` へ引き渡す（統括経由）。引き渡し自体の承認は不要（A分類機械検証＋ゲート①で承認済みの評価基準が担保 — `pcb-common` 第6節 共通ゲート③適用表：部品調査→回路設計：A）。採用判断は受け手の承認ゲート①で行われる。
9. **[A] ユーザー提供データの受入**: ユーザーが持つ見積・サンプル実績・購買条件等は、受入・記録・照合を本工程が実行する（A分類：受入・出典記録・candidates.csv 反映）。データ自体の入手は人の実行（C分類）であり、出典「ユーザー提供（取得: 人）」として記録する。

## 3.1 データ源の共通条件

- **記録義務**: 全てのデータ照会は「データ源名、URL、照会日時、版/rev、対象、取得ローデータの所在」を候補表に記録する（版/revの無いデータ源は「revなし」と明記する）。
- **整合性検査**: 同一部品についてデータ源間でスペック・在庫状態が乖離した場合は重大度A/Bとして扱い、より権威ある出典（メーカー公式 > 部品DB > ディストリビュータ表示）を優先して記録し、乖離を明記する。判定の妥当性に影響する乖離（必須段階の充足可否が逆転する場合等）は重大度Aとして扱う。
- **外部送信の注意**: 照会要求には要求仕様の断片が含まれ得る。外部送信が契約・機密保持上問題となり得る場合は、ゲート①のデータ源同意で範囲を確認してから照会する。
- **データ源が利用不能な場合**: 同意済みの代替源を用いるか、C分類（人が収集）へ切替えて依頼者へデータ要求を発行する。推測で補完しない。

## 3.2 部品属性の計算（初算）

候補表に付与する数値は、以下の共通式で初算する（詳細判断は受け手工程が行う）。仮定は全て明記する。

- **電流余裕率**: `I_rating ≥ I_max(要求) × 1.5`（コネクタ・電源IC）。
- **耐圧余裕率**: `V_rating ≥ V_max × 1.3`（一般部品）／ `≥ V_max × 2.0`（サージ・ESD耐量が要求される箇所）（要求がない場合は1.3を仮定し明記）。
- **消費電力と放熱初算**: `P = V_drop × I_avg`、`T_j = T_a + P × Rth(j-a)` で熱限界超過候補を除外する（Rth未記載は要確認）。
- **ESR初算**: デカップ用途は `ESR ≤ Z_target / N_decoupling` を目安にスクリーニングする（Nは候補表に記載）。
- **ライフサイクルスコア**: 量産中=100、NRFDP/NRND=70、EOL告知=20、代替品なしEOL=0。

## 4. 設計判断基準と計算方法

### 4.1 評価基準の三段構造

| 段階 | 内容 | 承認 |
|------|------|------|
| 必須（must） | 不充足なら候補から除外（電気仕様・環境等級・規制・パッケージ・調達条件） | ゲート①で承認 |
| 推奨（should） | 不充足なら条件付き適合（データ源・コスト傾向・熱・2次供給）と重み付きスコア化 | ゲート①で承認 |
| 参考情報（informational） | 判断の参考として記録するがスコア化しない（アプリノート・評価ボード情報等） | — |

### 4.2 判断基準（例）

| 判断事項 | 判断基準 |
|----------|----------|
| 候補の適合判定 | 必須段階の全項目充足が前提。推奨段階は重み付きスコアで順位付け |
| スペックの記載方法 | 出典（データ源名・URL・照会日時・版/rev）を必須記載とする。出典なし数値は「要確認」扱い |
| 入手性判定 | 複数供給源（2次供給含む）≧2、リードタイム ≤ 要求（要求未定時は16週を仮定し明記） |
| ライフサイクル判定 | EOL/NRND候補は代替品の有無を必ず併記。代替品なしEOLは不適合扱い |
| 乖離の扱い | データ源間で乖離する値は、優先順位（メーカー公式 > DB > ディストリビュータ）に従い採用し、乖離を明記 |

### 4.3 判断記録

調査計画、評価基準、データ源同意範囲、乖離時の出典優先判断、代替品評価に判断記録を作成する（共通フォーマット `pcb-common` 第7.3節）。**採用判断は本スキルでは行わない** — 候補の採用は `pcb-schematic-design` 承認ゲート①で行われる。

## 5. 使用するEDA・解析ツール

本スキルは設計データ生成を行わないため、EDAツールは使用しない。部品データ源の連携標準を定める。

| 用途 | ツール/データ源例 | 連携方式 | 自動化レベル |
|------|----------|----------|--------------|
| 候補検索 | ディストリビュータAPI・部品データベース（公開API／市販サービス。市販製品名はゲート①のデータ源同意で別途明記） | HTTP API（キーはゲート①同意済み） | A |
| スペック抽出 | データシートPDF/テキスト、メーカーサイト | PDF抽出・テキスト解析 | A（抽出）/ C（人が確認） |
| 在庫・リードタイム | ディストリビュータAPI、Web照会 | HTTP API / Web | A |
| ライフサイクル | メーカーPCN/EOL通知、部品DB（公開または市販サービス。市販製品名はゲート①で別途明記） | Web/API | A |
| 用户提供データ | 見積・実績・購買条件 | テキスト/表 | C（収集）+ A（受入・照合・記録: 第3節手順9） |

- APIキー・アカウントが無い場合、テキスト標準形式（CSV/YAMLの候補表）で人が収集したデータを受入れる（C分類切替）。代替手段とその限界（網羅性・鮮度の限界）を成果物に明記する。
- 照会レート制限の遵守、API利用規約の確認は本スキルの運用条件とする。
- **外部照会の実行手段**: 本パッケージの宣言ツールは `fs_read`/`fs_write`/`search`（manifest.yaml）であり、HTTP API・Web照会の実行手段は環境側の提供に依存する。実行手段が利用できない場合は上記の C分類切替へ移行し、その旨を判断記録（`pcb-common` 第7.3節フォーマット）に残す。外部照会の実行契約（APIキー／サブスクリプション取得）はC分類（第6節）。

## 6. 自動化する処理と人間が承認する処理

## 7. 成果物とファイル形式

- **成果物1**: `03_parts/部品調査パッケージ.md` — 構成: 目次（成果物一覧）、調査要求と制約、調査計画（検索キー・三段階評価基準・データ源一覧と同意記録）、候補表（MPN・メーカー・パッケージ・必須スペック照合結果・余裕率・入手性・ライフサイクル・総合判定・出典列）、乖離記録、データ源照会録（データ源・日時・対象・ローデータ所在）、不具合記録、判断記録、レビュー結果、承認記録、版数と変更履歴。
- **成果物2**: `03_parts/candidates.csv`（項目: 対象機能, MPN, メーカー, パッケージ, 必須スペック照合（各項目: 値と出典ref）, 余裕率, 在庫, リードタイム, 供給源数, ライフサイクル, 総合判定, 出典ref）。**ヘッダ命名規約**: 必須スペック照合の各項目は `spec_<項目名>` とし、その出典refは `spec_<項目名>_ref` とする（「出典ref」列には出典全体の参照 ID を記載）。この命名により共通第8.2節の自動突合がヘッダで機械的に実行できる。
- **成果物3**: `03_parts/sources.md` — データ源照会録（データ源名・照会日時・対象・ローデータの所在）と乖離記録。
- **成果物4**: 取得ローデータ（`03_parts/raw/`、参照される場合のみ）。
- 判断記録・レビュー結果は共通ルール（`pcb-common` 第7節）に従う。

## 8. 検証方法と品質基準

### 8.1 チェックリスト

共通チェックリスト（`pcb-common` 第8.2節）に加えて:

- [ ] 全てのスペック記載に統一書式の出典（データ源名・URL・照会日時・版/rev）が付いている（revが無いデータ源は「revなし」を明記）。
- [ ] 必須段階の照合は全候補・全項目で実施し、判定根拠が記録されている。
- [ ] 入手性・ライフサイクル情報に根拠（データ源・日時）があり、乖離が明記されている。
- [ ] 「要確認」項目の一覧と依頼者へのデータ要求が記録されている。
- [ ] 候補表の数値計算（余裕率・熱初算・ESR初算）は式・仮定・入力値つきで記録されている。
- [ ] 4大品質基準（完全性・整合性・追跡可能性・検証可能性）を満たす。

### 8.2 自己検証方法

- 出典なし数値のスキャン（「要確認」以外で出典refのない数値は不具合）。
- 必須段階不充足にもかかわらず「適合」判定の候補が無いか機械スキャン（受入条件）。
- 候補表（candidates.csv）とパッケージ文書の値の突合。

## 9. エラー発生時の対応

共通手順（`pcb-common` 第9節: 検出→記録→分類→修正→再検証→エスカレーション）に従う。本工程固有の注意事項:

1. **データ源間の乖離**: 重大度A/Bとして乖離記録に残し、優先順位（メーカー公式 > 部品DB > ディストリビュータ）に従って採用値を確定する。判定に影響する乖離は候補表に明記する。
2. **ライフサイクル情報が取得できない**: 「要確認」として記録し、入手性判定を「条件付き」とする。代替品候補の同時調査を実施する。
3. **必須スペックが判読不能**: 推測で埋めない。出典を明記した「要確認」項目として依頼者へデータ要求を発行する。
4. **外部照会の失敗・利用規約違反のおそれ**: 照会を中止し、代替データ源の同意を依頼する（ゲート①の再承認）。
5. **候補ゼロ**: 必須段階の基準が過剰でないか依頼者へ確認する（基準の再承認または対象部品の見直し）。S/A級は直ちに依頼元へ報告する。

## 10. 次工程への引き渡し条件

以下を全て満たした場合、回路図設計工程（`pcb-schematic-design`）へ引き渡す。

- [ ] 候補表（`03_parts/candidates.csv`）と部品調査パッケージが生成されている。
- [ ] 全てのスペック・入手性・ライフサイクル記載に統一書式の出典（データ源名・URL・照会日時・版/rev）が付いている（revが無いデータ源は「revなし」を明記）。
- [ ] 必須段階の照合が全候補・全項目で完了している（「要確認」は一覧化しデータ要求を記録）。
- [ ] 乖離記録が完備している（データ源間乖離の採用値と根拠）。
- [ ] 承認ゲート①（調査計画・評価基準・データ源同意）の承認記録が揃っている。
- [ ] 共通引き渡しチェックリスト（`pcb-common` 第10節）が全項目合格。
- [ ] 引き渡し後の採用判断は受け手工程（`pcb-schematic-design` 承認ゲート①: 部品選定）で行われる。本引き渡し自体は承認済み評価基準に基づく A分類の機械検証で担保する（`pcb-common` 第6節 共通ゲート③適用表：部品調査→回路設計：A）。
